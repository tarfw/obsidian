# TAR: Workspace Canvas & Operating Architecture
### Matter · Motion · Graph · Pipelines · Flow · Channels · Compiled Canvas · Turso Local-First · S3/R2 Vault · Cloudflare · OKF

## 1. Core Formulas & Non-Negotiables

```text
System = Matter + Motion + Graph + Pipelines + Flow + Channels + Canvas(Compiled)
Inbox(User) = Pending Approvals + Assigned Tasks & Orders + Join Invites + Direct Alerts
Outbox(Workspace) = Channel Replies + Inbox Delivery + External Integrations + Async Jobs
```

| Primitive | Role | Description & Examples |
|---|---|---|
| **Matter** | WHAT EXISTS | Contacts, products, orders, invoices, tickets, tasks |
| **Motion** | WHAT HAPPENED | Sales, stock, stages, messages, approvals |
| **Graph** | HOW RELATED | `works_at`, `assigned_to`, `supplied_by`, `stored_at` |
| **Pipeline** | STAGE MACHINE | Onboarding, sales, support |
| **Flow** | AUTOMATION | `validate` → `transact` → `reason` → `approve` → `execute` |
| **Channels** | CONVERSATIONS | WhatsApp, Telegram, Discord, Email groups |
| **Canvas** | THE SCREEN | Member's UI, compiled deterministically from role |

| Outbox Pillar | Destination | Purpose & Examples |
|---|---|---|
| **`Channel Replies`** | Chat Groups (WhatsApp, Telegram) | Conversational replies, confirmations & status updates |
| **`Inbox Delivery`** | Personal Turso DB (Mobile) | Assigned tasks, active orders & pending approvals (0ms offline) |
| **`External Integrations`** | 3rd-Party APIs (Stripe, Postmark) | Payments, refunds, courier dispatch & carrier labels |
| **`Async Jobs`** | Background Workers & S3 Vault | Stock rollups, cold S3 archiving, blob cleanup & timeout timers |

| Invariant | Definition |
|---|---|
| **Membership join** | `contact matter` + `onboarding pipeline` *(nothing else creates a member)* |
| **Canvas(member)** | Workspace canvas filtered to member role |
| **Channel replies** | **Outbox-only:** Every conversational reply/alert routes via `outbox`; zero inline HTTP |
| **Local-first set** | Personal operational data only (inbox, assigned tasks & active orders); catalogs cache via TTL |
| **AI path** | Channel chat; optional elsewhere |
| **Canvas path** | TarApp native components; deterministic compile (skips AI) |

**Non-negotiable rules**

1. Turso owns state (matter/motion/graph). S3/R2 owns blobs. OKF owns markdown specs. D1 owns auth & routes.
2. Tarai (Cloudflare Worker) is the sole authoritative write path. TarApp never receives workspace write keys.
3. Every mutation is idempotent; matter update + motion append commit atomically.
4. AI may propose; deterministic code validates and executes. High-risk actions require owner 1-tap approval.
5. Authorization checks precede every read, write, projection, and AI context assembly.
6. IDs stable/prefixed, timestamps server UTC integers, money integer minor units, deletes = tombstones first.
7. Turso Sync provides local-first transport; TAR builds no custom merge engine.
8. Channel replies & side-effects are strictly Outbox-driven (zero inline external HTTP calls from AI/webhooks).

### 2.1 Matter Tripartite Storage (Turso · S3/R2 · OKF)

```text
Matter Entity = Operational State (Turso) + Media Vault (S3/R2) + Knowledge & SOPs (OKF)
```

| Tier | Engine | What It Holds | Access Model |
|---|---|---|---|
| **Operational State** | **Turso DB** | IDs, status flags, JSON attributes & storage pointers | Synced to phone replica (0ms local lookups) |
| **Media Vault** | **S3 / R2** | Heavy files, photos, audio, PDFs & cold archives | Short-lived presigned URLs generated by Tarai |
| **Knowledge & SOPs** | **OKF (R2)** | Rich text guidelines, specs, wiki docs & canvas.md | Human-editable plain markdown; AI context |

#### Storage Pointer Envelope (`matter.data`)

```json
{
  "attributes": { "name": "Smash Burger", "price_cents": 1400 },
  "storage_pointers": {
    "okf_doc": "catalog/recipes/burger.md",
    "blobs": [{ "key": "vault/w1/m_104/photo.webp", "sha256": "e3b0c4...", "mime": "image/webp" }]
  }
}
```

#### Ingest & Fetch Protocol
1. **Direct Upload:** Client gets 5-min presigned URL from Tarai → uploads file to S3/R2.
2. **Atomic Commit:** Client issues typed action → Tarai atomically saves `matter` pointer + `motion` append.
3. **Fast Read:** TarApp renders card from local Turso (0ms) → streams heavy media only on tap.
4. **Orphan GC:** Background sweeper prunes uncommitted S3/R2 uploads weekly.

## 4. Membership Lifecycle (Onboarding & Offboarding)

```text
Membership = Contact Matter + Onboarding Pipeline
Formula: Phone / Handle ──► Inbox Accept ──► Owner 1-Tap Role = Member
```

### 4.1 The 3-Step Onboarding Flow

```text
1. CONNECT    Person provides Phone / Handle (or Owner creates Contact)
      │
      ▼
2. ACCEPT     Outbox delivers invite ──► Person taps [Accept] in Personal Inbox
      │
      ▼
3. PROVISION  Owner selects Role (1-tap) ──► Tarai grants D1 access
                • Canvas & switcher unlock on member's phone (0ms)
                • [Outbox] Auto-adds member to team chat groups
```

### 4.2 Universal Offboarding (1-Tap Cutoff)

```text
Owner removes member ──► Tarai revokes D1 authority instantly
  • Auth token dies; phone purges local replica & canvas cache on sync / push
  • [Outbox] Auto-kicks member from team chat groups (WhatsApp, Telegram)
  • Motion audit trail & historical activity are permanently retained
```

| Principle | Rule |
|---|---|
| **Universal Path** | **Phone/Handle → Inbox Accept → Owner 1-Tap → Member** (no backdoor bypass) |
| **Instant Setup** | Approved member's workspace switcher unlocks and renders role canvas immediately |
| **Instant Cutoff** | Revocation kills D1 tokens and wipes local device replica on sync / silent push |

### 6.2 canvas.md — Declarative Workspace Spec

One presentation-only markdown/YAML spec per workspace stored in OKF (no SQL, auth logic, or secrets):

```yaml
schema: 1
version: 14
workspace: w_casa_verde

blocks:
  - id: shift-sales
    components: [metric_card, chart_bar]
    data: [motion/sales_today]
    roles: [owner, manager]
  - id: active-orders
    components: [list_card]
    data: [matter/orders]
    roles: [manager, cashier, waiter]

actions:
  pos.new_order: {screen: form, fields: [items, payment], roles: [cashier, manager], chip: true}
  stock.adjust:  {screen: form, fields: [sku, delta], roles: [manager, owner], chip: true, confirm: true}
  member.invite: {screen: form, fields: [phone, role], roles: [owner], chip: true}
```

### 6.3 Generative Role Resolution

```text
Canvas(role R) = select(blocks + chips + actions, where declared_roles includes R)
```

| Step / Rule | Behavior |
|---|---|
| **Compile Trigger** | Executed once per `(workspace, role, canvas.version)` by Tarai |
| **Output Artifact** | Deterministic JSON manifest cached on-device (keyed by `sha256(canvas_json)`) |
| **Filtering Rule** | Unauthorized entries are omitted *(never rendered greyed-out)* |
| **Fallback Rule** | Owner sees full canvas; unknown roles fail closed |

## 7. Workspace Switcher & On-Device Manifest Cache

D1 exclusively owns workspace memberships, roles, and DB routes. On membership events, Tarai syncs `membership` rows to the user's Personal DB for 0ms offline switching:

```text
TARAPP LOCAL STORE (Personal DB Replica) /
├── membership table   ──► ws_id, name, role, is_owner, db_route, canvas_hash
└── canvas_manifests/  ──► {canvas_hash}.json (compiled role UI manifest)
```

| Rule | Specification |
|---|---|
| **Cold/Warm Switch** | Query local `membership` table + load cached `{canvas_hash}.json` *(0ms local disk)* |
| **Hash Refresh** | On sync: compare local `canvas_hash` with D1/Tarai; cache miss fetches updated JSON manifest |
| **Instant Cutoff** | D1 membership revoked → auth token dies → phone purges local replica & manifest cache on sync |

## 8. Turso Local-First Sync (Selective Offline Set)

```text
Local-First Formula: sync_to_device(x) = needed_personally_offline(x) OR my_own_data(x)
Transport Engine:    Local SQLite + Turso CDC push()/pull() + Last-Push-Wins (LPW)
```

| Category | Datasets | Sync Model | Conflict Rule |
|---|---|---|---|
| **Device-Local (Synced)** | • Personal matter (notes, drafts, preferences)<br>• Unified Personal Inbox (tasks, approvals, orders) | ✅ Full offline sync / projected | Turso Last-Push-Wins (LPW) for personal data; HTTP retry queue for workspace edits |
| **Cloud-Streamed (Cached)** | • Catalogs & contacts cache (TTL / ETag)<br>• Heavy media, binary blobs & historical ledgers | ❌ Stream on demand | Server truth (TTL cached in client SQLite, never replicated via Turso CDC) |

* **Workspace Writes:** Local read only; writes are queued with idempotency keys in SQLite retry queue.
* **Hot Counters:** Balances & inventory recomputed server-side from snapshot + tail motions (no cell-level LPW overwrites).
* **Teardown:** Logout / revocation immediately erases local replica and stops token refresh.

| Policy Dimension | Rule & Behavior |
|---|---|
| **Local-First Formula** | `sync_to_device(x) = needed_personally_offline(x) OR my_own_data(x)` |
| **Write Classes** | • **My Data:** Local write → Turso Last-Push-Wins (done)<br>• **Workspace Data:** Local READ only; write = queued HTTP request in SQLite retry queue *(idem key survives offline)* |
| **Contention Rule** | Hot counters (stock, balance) are **recomputed** from periodic rollup snapshots + appended motions server-side ($O(\text{recent tail})$); never edited as plain cells, preventing LPW collisions |
| **Sync Lifecycle** | Boot offline → start from disk. Cadence: foreground / resume / network-recover / manual + modest session timer *(no 5s polling)* |
| **Teardown** | Logout / revocation → close + erase replica; revocation terminates token renewal immediately |
| **Security** | Device DB encrypted at rest; keys in platform secure store; tokens short-lived, DB-scoped, via Tarai |

Projection minimization stays mandatory (roles/fields/redaction/expiry/tombstones) because downloaded bytes cannot be un-read; sync provides automatic, bandwidth-efficient delivery.

## 9. Canonical Schema (tenant DBs)

Core tables shared by Personal and Workspace DBs; both reuse identical `matter/motion/graph` shapes.

```sql
CREATE TABLE matter (
  id TEXT PRIMARY KEY, type INTEGER NOT NULL,
  data TEXT NOT NULL CHECK(json_valid(data)),
  state INTEGER NOT NULL DEFAULT 1, version INTEGER NOT NULL DEFAULT 1,
  created INTEGER NOT NULL, updated INTEGER NOT NULL, deleted_at INTEGER);

CREATE TABLE motion (
  id TEXT PRIMARY KEY, type INTEGER NOT NULL, actor TEXT NOT NULL, ref TEXT,
  data TEXT NOT NULL CHECK(json_valid(data)), idem TEXT NOT NULL UNIQUE,
  payload_hash TEXT NOT NULL, created INTEGER NOT NULL);

CREATE TABLE graph (
  id TEXT PRIMARY KEY, source TEXT NOT NULL, target TEXT NOT NULL,
  kind INTEGER NOT NULL, version INTEGER NOT NULL DEFAULT 1,
  created INTEGER NOT NULL, updated INTEGER NOT NULL, deleted_at INTEGER);

CREATE TABLE inbox (            -- Personal DB only
  id TEXT PRIMARY KEY, user_id TEXT NOT NULL, workspace_id TEXT,
  type INTEGER NOT NULL, title TEXT NOT NULL, ref TEXT,
  priority INTEGER NOT NULL DEFAULT 1, status INTEGER NOT NULL DEFAULT 1,
  data TEXT DEFAULT '{}', version INTEGER NOT NULL DEFAULT 1,
  created INTEGER NOT NULL, updated INTEGER NOT NULL, deleted_at INTEGER);

CREATE TABLE membership (       -- Personal DB only; workspace switcher index
  workspace_id TEXT PRIMARY KEY, name TEXT NOT NULL,
  role TEXT NOT NULL, is_owner INTEGER NOT NULL,
  db_route TEXT NOT NULL, canvas_hash TEXT NOT NULL,
  version INTEGER NOT NULL DEFAULT 1, updated INTEGER NOT NULL);

CREATE TABLE projection (       -- Personal DB only; authorized read models
  id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL, collection INTEGER NOT NULL,
  source_id TEXT NOT NULL, type INTEGER NOT NULL,
  data TEXT NOT NULL CHECK(json_valid(data)),
  source_version INTEGER NOT NULL, expires INTEGER, updated INTEGER NOT NULL,
  deleted_at INTEGER, UNIQUE(workspace_id, collection, source_id));

CREATE TABLE request (          -- Workspace DB only; idempotency & approval state
  idem TEXT PRIMARY KEY, actor TEXT NOT NULL, action TEXT NOT NULL,
  payload_hash TEXT NOT NULL, status INTEGER NOT NULL, required_role TEXT,
  response TEXT, created INTEGER NOT NULL, completed INTEGER, expires INTEGER);

CREATE TABLE outbox (           -- external effects after commit
  id TEXT PRIMARY KEY, kind INTEGER NOT NULL, destination TEXT NOT NULL,
  payload TEXT NOT NULL CHECK(json_valid(payload)), idem TEXT NOT NULL UNIQUE,
  status INTEGER NOT NULL DEFAULT 1, attempts INTEGER NOT NULL DEFAULT 0,
  next_attempt INTEGER NOT NULL, lease_owner TEXT, lease_until INTEGER,
  provider_ref TEXT, last_error TEXT,
  created INTEGER NOT NULL, updated INTEGER NOT NULL);

CREATE INDEX idx_matter_live
  ON matter(type, state, updated DESC) WHERE deleted_at IS NULL;
CREATE INDEX idx_motion_ref
  ON motion(ref, created DESC, id) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX unq_graph_live
  ON graph(source, target, kind) WHERE deleted_at IS NULL;
CREATE INDEX idx_inbox_pend
  ON inbox(user_id, status, priority DESC, created DESC)
  WHERE deleted_at IS NULL;
CREATE INDEX idx_outbox_due
  ON outbox(status, next_attempt) WHERE status IN (1,4);
```

Pipelines/flows persist as versioned `matter(type=9,10)` records plus a small `job` helper table for leases. Generic `matter.data` payloads are validated against a strict, versioned JSON Schema registry in Tarai per type code. Hot fields (SKU/barcode/stage/due) get versioned expression indexes. Multi-tenant DBs track migrations via a `_schema_version` table; schema updates run via provisioning workflows. Optimistic concurrency via `version`; stale write ⇒ `409` with current state.

| Step | Phase | Action & Idempotency Rules |
|---|---|---|
| **1** | **Auth & Resolve** | Authenticate → authorize (D1 membership + role) → resolve tenant DB (Trace ID = `idem`) |
| **2** | **Pre-Validate** | Validate request against JSON Schema registry; compute `payload_hash` |
| **3** | **Idempotency Lock** | `BEGIN; INSERT INTO request(idem, payload_hash, status='processing')`<br>• *Same key + same hash + completed:* Replay stored canonical response<br>• *Same key + different payload hash:* `409 Conflict`<br>• *Concurrent in-flight:* Return `409 Conflict` (`Retry-After: 1s`); client queue retries |
| **4** | **In-TX Validate** | Validate entity versions, limits, and policy **inside** transaction |
| **5** | **Mutate & Audit** | Update `matter` / `graph` → append `motion` *(server UTC timestamp; deterministic keys)* |
| **6** | **Stage Effects** | • *Direct write:* Enqueue `outbox` rows (external delivery/sync)<br>• *Approval required:* Mark `request.status = pending_approval` + enqueue `outbox(kind=notify_approval)` for Inbox Delivery to approver |
| **7** | **Commit & Respond** | Store canonical response in `request` table → `COMMIT` |

| Tier | Examples | Behavior |
|---|---|---|
| **Read** | Canvas blocks, searches, media streaming | Authorized fact slices, presigned URLs, 0ms local reads |
| **Direct Write** | Task update, order entry, stock adjust | Execute on request; optional client confirmation sheet (`confirm: true`) |
| **Approval-Required** | Payments, refunds, `member.remove`, credentials | Enters `request.status = pending_approval`; creates inbox task for `required_role`; resumes atomic execution on owner 1-tap |

## 11. Guardrails & Architecture Bounds

| Area | Non-Negotiable Contract |
|---|---|
| **Secrets & Keys** | Zero secrets in TarApp / `EXPO_PUBLIC_*`. Database tokens are read-only, short-lived, DB-scoped. |
| **Untrusted Input** | Webhooks, chat messages, forms, and AI outputs are signed, validated, and rate-limited. |
| **Multi-Tenancy** | Strict tenant isolation via signed workspace routing and per-workspace quotas. |
| **Observability** | `x-trace-id` = client `idem` key propagated end-to-end (Worker → DB → Outbox → Delivery). |
| **Data Retention** | Inbox items retained until resolved (30d tombstone); financial & motion audits permanently kept. |
| **Blob Security** | S3/R2 presigned URLs bound by size, sha256 checksum & 5-min expiry; weekly orphan GC sweeper. |

#### Release Gates & Definition of Done
- **Role Isolation:** Every member sees only their authorized canvas surface
- **Instant Cutoff:** Offboarding revokes D1 access and wipes local device replica immediately
- **Offline Resilience:** App operates offline for 7+ days and reconciles cleanly upon sync
- **Strict Idempotency:** Duplicate inputs, retries, or webhooks never duplicate a side-effect
- **Audit Provenance:** Every write is permanently attributable to `(user_id, role, version)`
